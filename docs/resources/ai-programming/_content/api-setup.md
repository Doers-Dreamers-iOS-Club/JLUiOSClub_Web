这一篇，我想带大家做一件简单的事：把自己的模型服务接到 DSH 里，发出一条消息，再从这次操作认识常见的 API 名词。

我们先用界面完成连接。以后在 ZCode 或其他工具里遇到 API Key、Base URL、Model 这些字段，就知道它们各自负责什么。

## 第一步：准备 DSH 与 API 密钥

从 [DeepSeek 官网的 Harness 页面](https://www.deepseek.com/harness/)进入桌面端下载。已经安装的同学，直接打开应用。

再打开 [DeepSeek API 控制台](https://platform.deepseek.com/)，登录后找到 API keys 或密钥管理入口，创建自己的密钥。查看当前可用余额或额度，再继续连接。

这里的 API Key 是让软件调用模型的凭据。把它填进工具的密钥栏，自己保管；需要分享配置截图时，把这部分遮住。

## 第二步：在 DSH 中连接 DeepSeek

打开 DSH 的“设置 → 模型”，找到 DeepSeek 提供商卡片，把刚才创建的 API Key 填进去并保存。

内置提供商会带好对应的服务配置。先用这条最短路径：选提供商，填自己的密钥，保存，再选择模型。设置中已经有默认值的项目，先沿用。

回到会话界面，选择 DeepSeek 下的可用模型，新建一轮对话。可以发送：

```text
请用三句话解释 API，并说明它在我使用的编程 Agent 中做了什么。
```

收到正常回答后，我们就完成了一次模型调用。保存配置之后要实际发一条消息，才能知道这组配置能否工作。

接着回到自己的项目，发一个很小的任务，例如“请阅读项目说明，概括当前做到了哪一步”。这样就把模型连接接回了前面的协作过程。

## 第三步：认清最常见的几个字段

如果以后接入其他服务，或者打开自定义提供商表单，通常会遇到这些名称：

| 常见名称 | 它回答什么问题 | 这次可以怎样理解 |
|---|---|---|
| Provider / 提供商 | 模型由哪家服务提供？ | 这里选择 DeepSeek |
| API Key / 密钥 | 用哪个账号的凭据调用？ | API 控制台创建的密钥 |
| Base URL / 服务地址 | 请求发到哪里？ | DeepSeek 对话接口的基础地址是 `https://api.deepseek.com` |
| Model / 模型 ID | 具体调用哪个模型？ | 按可用列表选择；官方示例使用 `deepseek-flash` |
| Protocol / API 协议 | 双方按哪种格式交换信息？ | 选择提供商文档规定的接口格式 |

服务地址、协议和模型 ID 要与同一份服务说明对应。通常先选内置提供商最方便；确实需要自定义时，再对照[官方 API 配置说明](https://api-docs.deepseek.com/zh-cn/)逐项填写。

遇到“兼容格式”这个说法，可以理解为服务采用某种已有接口的请求与返回规则。例如 OpenAI Chat Completions 是一种接口格式名称，选择这种格式仍可以调用兼容它的 DeepSeek 服务。

网页聊天地址与 API 服务地址也分开看：前者供人打开聊天页面，后者供软件发送请求。配置 Base URL 时，使用 API 文档里的地址。

## 第四步：看懂一次调用发生了什么

```text
你在 DSH 输入一条消息
        ↓
DSH 按选定模型和服务配置发出请求
        ↓
服务检查凭据、处理请求，返回结果
        ↓
DSH 把回答显示在对话中
```

这次调用里，DSH 已经替我们处理了请求组织和结果显示。API 就是这条信息交换的接口。以后自己写程序时，也可以完成同样的交换，只是由自己的代码负责发送和读取。

在界面里，先认识请求和响应两个词：Request 是发出去的信息，Response 是服务返回的信息。提示词属于请求的一部分；返回的回答与用量信息属于响应。

## 第五步：认识费用和能力相关的词

| 名词 | 先理解到什么程度 |
|---|---|
| Token | 模型处理输入和输出的计量单位之一，不能直接按汉字数换算 |
| Input / Output | 发给模型的输入与它生成的输出，可能分别计算用量 |
| Context Window / 上下文窗口 | 一次处理可容纳的信息规模，与已经学过的上下文有关 |
| Max Tokens / 输出上限 | 限制生成长度的参数之一，不是精确字数要求 |
| RPM / TPM | 每分钟请求数或 token 数等速率限制 |
| Balance / Quota | 余额或可用额度，去对应服务的控制台查看 |
| Streaming / 流式输出 | 结果逐步返回，界面可以逐步显示文字 |

现在能把字段认出来，知道去哪里找对应值就可以。之后遇到长对话、响应过慢或额度问题，再带着具体问题深入。

## 连不上时，先按提示检查

| 现象 | 先看哪里 |
|---|---|
| 保存后仍没有可用模型 | 提供商是否配置完成，模型是否选中 |
| 认证失败或 401 | 密钥、提供商和服务地址是否对应 |
| 余额不足或 402 | API 控制台中的余额与额度 |
| 参数错误或 400 / 422 | 协议、模型名称与其他参数 |
| 请求过于频繁或 429 | 调用频率与并发，稍后再试 |
| 超时或连接失败 | 网络、地址及服务状态 |

具体状态码可以查[官方错误说明](https://api-docs.deepseek.com/zh-cn/quick_start/error_codes/)。如果向同伴或 Agent 求助，带上工具、提供商、模型名、错误文本，以及已经尝试过的办法。

## 换一个工具，看看能否认出来

在另一款工具中找到模型配置页，试着指出：哪里选提供商，哪里填密钥，哪里是地址与模型名。界面可以不同，我们刚才认识的几种关系仍然可以用来判断。

最后用自己的话回答三个问题：密钥从哪里来？模型请求发到哪里？怎样确认连接完成？如果能说明，并且已经收到一条正常回答，这次接入就走通了。
